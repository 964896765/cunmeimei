# 预约申请编号与本机恢复

日期：2026-11-02。本轮继续原工程，保留21页、五导航、现有主题与配色。新增025迁移，仅在一次性隔离数据库执行；没有升级持久开发库、连接服务器或发布小程序。

## 用户可见变化

- 在线预约在发送前先保存原申请，包含服务、日期、时段、备注和独立申请编号。保存失败不发送请求，并提供重新读取恢复记录的入口。
- 离开页面后重新进入，恢复待核对状态，不自动提交；“我的预约”也提供“继续核对原申请”。记录按账号、API地址与验收模式隔离。
- 核对通过专用编号接口，不再从最近100条预约里按时段猜测。服务暂停公开时，核对入口仍然可用。
- 找到已取消、超时、拒绝或完成的原预约，会显示其真实状态；重试不会自动创建一笔替代预约。服务、时间或备注不能用原编号更换。
- 确认没有创建预约的拒绝结果也绑定编号。时段冲突后，即使对方取消、服务恢复，延迟的旧请求也不能变成新预约；用户重新申请时使用新编号。
- 本人数据导出增加预约记录及申请结果，含本人申请编号、关联预约与拒绝原因码。

## 服务端与迁移

`POST /api/v1/bookings` 增加可选 `clientKey`（16–64位字母、数字、下划线或短横线）。新客户端始终发送；旧的无编号请求保留原规则，不能获得新恢复保证。

新增 `GET /api/v1/me/booking-submissions/:clientKey`，要求本人登录。返回 `{booking,replayed:true}`，或已经记录的 `{rejected:true,clientKey,errorCode}`。没有记录返回404 `BOOKING_SUBMISSION_NOT_FOUND`；这不等于原请求失败，客户端继续保留待核对状态。

新增 `025_booking_submissions.sql`：申请表关联账号与预约、保存规范化请求的SHA256、成功关联或确定拒绝结果。原001–024未改写，不为历史预约编造编号。复合外键限制预约归属，账号状态触发器阻止关闭账号的新写入。

同一账号和编号在事务锁内处理：先检查已保存结果，再判断能否新预约；预约与申请结果一起提交，写入申请结果失败时预约回滚。时段唯一约束继续处理不同申请之间的争抢。同一账号、同一时段、相同内容的不同编号可以关联同一有效预约；不同备注明确拒绝。确定拒绝同样提交到申请表，防止迟到的旧请求重新生效。

成功映射始终返回原预约的当前状态；确定拒绝保留原决定。确认结果后清理本机快照，清理失败会保留已确认回执并提供重试，不伪装成提交失败。内存驱动只用于测试，其服务端映射不会跨进程重启保存；正式恢复依赖PostgreSQL。

## 仍需验收的边界

恢复记录存在本机小程序存储，清缓存、卸载和换设备不继承。请求编号是幂等标识，不能代替身份认证；本机存储没有被宣称为加密保险箱。每账号/API/验收模式最多保留30个不同服务的待核对记录，达到上限后先核对，不自动丢弃未知结果。

成功、拒绝与业务档案没有自动过期删除；生产保留期限、定向删除与备份制度仍需制定。未为旧请求推断历史编号，也没有新增支付、商家提醒或自动派单。

上线需要同时部署新后端、显式应用025并发布新客户端。当前本地API配置保持开发用途，现有持久库没有自动升级；不可只更新客户端就认定真实后端已支持新接口。生产域名、微信真实登录、Android/iPhone杀进程/弱网/存储满/账号切换、生产容量与备份告警继续受 [上线门禁](V1_RELEASE_GATE.md) 约束。
