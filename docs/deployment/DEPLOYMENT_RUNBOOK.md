## 4. 安装与配置（后续批准步骤）

1. 依审查制品安装必要Docker Engine/Compose、Nginx及证书工具，避免无必要服务；SSH最小来源、密钥登录、保持应急通道，规则变更后复验。
2. 按环境文档在源码外安全生成运行/迁移/备份配置，设置文件权限；不把秘密放在CLI参数、工单、前端或镜像。创建源码外私有附件目录、PG持久卷、专属网络。
3. 初始化/升级按DATABASE_MIGRATION_PLAN实施，运行角色无超级权限；不把现有开发数据卷当生产卷。不执行任何带`-v`的全栈删除。
4. 安装证书，SAN覆盖实际使用的apex和api名称；仅 `*.dgqfl.xyz` 不覆盖apex。先 `nginx -t` 后reload，校验完整链与自动续签/到期告警。证书失败不降级明文承载登录。
5. 核实代理至容器的真实TCP来源后配置TRUSTED_PROXY_IPS，仅信该代理并覆写X-Real-IP。验证伪造头无法改变限流主体。
6. 先运行preflight和只读db:check，再启动单API，配置定时加密异地备份与外部告警；检查资源/网络约束实际生效，不只看YAML。

## 6. 更新与故障

- 每次发布固定镜像digest、备份点、schema清单和操作记录；停写/迁移完成后检查ready及关键业务，再恢复流量。单实例有短暂停机，选择维护窗口，不承诺零停机。
- ready连续失败、OOM或大量5xx时停止放量，保留脱敏日志和旧镜像。容器unhealthy不会自行恢复，需明确值守与响应流程。
- 应用回滚先验证schema兼容；数据库恢复只能到新库，保留原库，处理备份后写入差异。不得通过清卷、删除迁移历史或覆盖现有库“回退”。
- 每日检查备份成功、磁盘、容器重启、审核积压、联系待办；每月恢复演练和权限复查。告警通知通道及收件人须用户明确授权后配置，本轮未向任何人发送消息。
