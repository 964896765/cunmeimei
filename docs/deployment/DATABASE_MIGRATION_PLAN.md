## 已实现机制

`backend/src/schema-migrations.js`按文件名顺序载入SQL并计算SHA256，历史保存在 `schema_migrations`；同一连接持有session advisory lock，逐文件BEGIN/COMMIT并写历史。已有文件校验和改变或出现未知迁移会阻止执行。

每文件独立事务：第N个失败会回滚该文件，之前成功文件已提交，不能声称整批全回滚。没有down迁移，也不能通过删除历史记录重新跑SQL。启动先verifySchema，未升级/漂移会阻止启动；地区仅在空表种子初始化，正式业务数据不会由启动脚本自动补齐。

## 首次生产初始化

1. 核实目标磁盘/地域/备份位置，创建专属持久卷；绝不挂载已有未知卷尝试初始化。
2. 一次性初始化账号创建DB，配置迁移角色、运行角色、备份角色；运行角色无超级用户/建库/DDL权限。现仓库无角色授权制品，先生成并在隔离环境验证迁移及正常DML。
3. 从CI镜像使用独立迁移环境执行001–024，检查迁移清单/校验和、对象权限、序列默认权限；初始化账号不进入API配置。
4. 用运行角色执行只读check、启动API检查ready，确认地区种子正确；不得导入本地测试账号、演示商家、假电话和测试积分。
5. 建立首次基线备份并在新空库恢复，验证解密与媒体引用，方可开放正式写入。

## 现有数据库升级顺序

1. 确认是开发库还是生产库，记录主机/库名/版本/schema，不记录连接串密码；统计关键表行数、大小及当前功能开关。
2. 先做加密完整备份，含PG、私有文件、密钥与角色授权记录；验SHA256并确认异地副本可读取。
3. 在隔离库恢复备份，使用同一发布镜像升级018–024（或该库实际缺失项）；记录耗时、锁等待、空间增长、权限和数据不变量，跑严格PG及权限/端到端回归。
4. 批准维护窗口后暂停写流量、停止后台定时写任务，并做最终备份；迁移前确认无其他发布者。advisory lock不替代停写和业务一致性设计。
5. 一次性迁移任务运行，保存脱敏结果；检查缺失/漂移/未知列表均空，再启动新API。
6. 验收登录、内容审核、电话授权撤销、统一待办、举报、申诉、账户注销/数据权利、积分账本一致性与媒体权限，观察后恢复流量。

## 备份和恢复能力

已有 `backend/src/database-recovery.js`：PG custom格式dump + `.sha256`，文件独占创建且权限0600；工具凭据通过子进程环境传递，不写命令参数。恢复限制新空 `restore_drill_*` 库、先验hash，再 `pg_restore --single-transaction --exit-on-error`，不使用 `--clean`。

缺失能力：dump没有加密、没有定时任务/OSS上传/失败通知，没有全局角色备份、附件快照、密钥托管、连续WAL归档和PITR。hash仅防意外损坏，不是保密或可信签名。

后续计划：宿主systemd timer每日错峰备份，PG16客户端；加密后上传独立私有OSS备份桶，密钥分开保管。建议初始保留7份日备、4份周备、3份月备，结合数据权利/保留政策审核。每日确认最新成功时间与大小异常；每月至少恢复一次并计时，发布前也要恢复演练。备份临时空间应覆盖dump及加密中间文件；不足时先实现经过校验的流式加密上传或扩盘。

恢复必须带上私有附件、电话加密密钥和应用版本/迁移manifest；PG里的图片包含在dump中，未来OSS对象需额外版本/对象清单。升级/媒体写入期间保持一致性快照或短暂停写，不能把不同时刻的DB和附件拼成“完整备份”。普通应用dump `--no-owner --no-acl` 不会恢复角色授权，恢复后应重新应用经审核的角色脚本。

## 失败和回退

- 校验和漂移/未知迁移：停止发布，保存证据并调查；不改历史、不删除数据、不强制重跑。
- 某文件失败：检查该文件事务回滚和已提交清单，修复需新增前向迁移或受审查的处理方案；不能假设库仍是升级前版本。
- 应用回滚：先证明旧镜像兼容新schema；不兼容时继续维护，恢复备份到新库、核对权限与数据，再受控切换连接。保留原库供调查，不覆盖恢复。
- 开放写入后回退到备份会丢失备份后的合法业务写入，须先冻结、导出差异并制定补偿/重放策略，不能静默回退。初始RPO≤24h、RTO≤4h只是待演练确认的目标。
