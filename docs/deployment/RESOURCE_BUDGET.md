# 2GB服务器资源预算与容量门槛

日期：2026-11-01。以下为待压测的初始预算，不是实测吞吐承诺；4GB swap不能替代RAM。

## 内存和CPU

| 组件 | RAM预算/硬上限 | 初始建议 |
| --- | ---: | --- |
| Ubuntu、Docker、SSH等宿主开销 | 384MiB预算 | 无需常驻编译/监控全家桶 |
| Nginx | 64MiB预算 | 宿主服务，可后续systemd约束并验证 |
| 单API容器 | 640MiB硬上限 | CPU0.75，V8 heap约256MiB，为Sharp/native/buffer预留空间 |
| PostgreSQL容器 | 640MiB硬上限 | CPU1.0，shared_buffers128MiB、work_mem2MiB、maintenance_work_mem32MiB、max_connections30 |
| 空闲余量 | 320MiB | 覆盖短峰、备份读取与宿主波动 |
| 合计 | 2048MiB | 必须在真实目标机验证RSS、cgroup使用与OOM |

Compose使用本机执行确实支持的 `mem_limit`、`cpus`，部署后inspect确认；不能只写未生效的Swarm资源声明。`NODE_OPTIONS=--max-old-space-size=256`仅约束V8，不约束Sharp/libvips与Buffer。

API连接池当前最大10，迁移池2；单API足够，无PgBouncer必要。30连接是初始DB总上限，要留维护/迁移/备份余量。`work_mem`按查询节点和并发多次分配，不能按每连接一次计算。运行角色建议设置经验证的语句/空闲事务超时；后台长操作单独评估。

## 图片为首要内存风险

当前单次请求字节最多2MB，但允许3600万输入像素；解码后内存远大于上传体积，且两份图的处理涉及native内存。每日30张配额在解码后才检查，无法挡住大量失败解码的资源消耗。

上线前应完成：网关上传接口全局并发先设1、同时按来源限流；业务层增加有上限且可拒绝的解码并发门；评估降低像素上限、尽早配额/身份校验和解码超时。全局限制需覆盖经过Nginx的全部上传，并保证API端口不能公网绕过。当前源码尚未实现业务并发门。

压测至少覆盖：大像素小文件、畸形图片、同时上传与分页搜索、账户导出、备份同时运行。记录p95、拒绝率、RSS/native峰值、连接数、PG锁等待和容器OOM。初始建议门槛：无OOM/重启、持续保留至少约200MiB宿主可用内存、无持续换页、普通查询p95满足另行约定目标。若640MiB API容器仍无法稳定处理支持的图片，应先收紧支持范围或升级4GB，不能只提高V8堆。

## 40GB磁盘预算

| 用途 | 初始容量包络 |
| --- | ---: |
| 系统、运行软件及保留镜像 | 8GiB |
| PostgreSQL数据/索引/WAL | 10GiB |
| swap | 4GiB（用户报告，待核实） |
| 应用与代理日志 | 1GiB |
| 备份临时落盘 | 2GiB |
| 临时文件/附件 | 2GiB |
| 空闲及扩展预留 | 约13GiB |

标称GB与系统GiB有差异，应按实际 `df` 重算。图片入库时DB、WAL、备份均增长，10GiB不是可承诺业务容量。备份及加密临时文件可能同时存在，**2GiB只适用于实际dump与中间文件合计能装下的阶段**；超过前须实现加密流式异地备份、调整配额或扩盘，不能等磁盘满。

## 运维限制与告警

- Docker日志建议json-file每文件10MiB、保留3份；Nginx/systemd日志设轮转与保留上限，敏感请求不记录body/query/token。
- 初始告警建议磁盘>70%预警、>85%停止非必要写入并处置；连续ready失败、5xx上升、OOM、备份过期或失败立即通知。告警阈值需在试运行调整。
- 正式机不运行npm安装、原生编译、微信自动化或全套集成测试；在CI产生目标架构镜像。部署时预留旧/新两份镜像空间。
- 定时任务错峰：备份、附件巡检、维护批处理避免峰值重叠。恢复演练优先隔离环境，若在同机须另算磁盘/RAM并安排维护窗口。
- 不执行广域volume清理、`down -v`、无差别image prune。数据和备份保留由明确对象清单与验证结果决定。

备份初始目标建议RPO≤24小时、RTO≤4小时，需由实际恢复计时验证并得到业务认可；若不满足，调整频率/资源或采用托管数据库。当前没有持续归档/PITR能力，不能承诺按任意时间点恢复。
