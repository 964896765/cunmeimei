## 四类位置分开处理

| 上下文 | 存储/使用规则 |
| --- | --- |
| 浏览城市 | 本机 `city_life_browse_city`，使用城市/区划编码，用户手动选择优先；历史最多6个城市 |
| GPS位置 | 仅主动调用 `wx.getLocation({type:'gcj02'})` 后保留在应用内存，不自动覆盖浏览城市，不持久化精确住址 |
| 发布地点 | 表单单独确认城市并存入该信息 `attributes.cityCode/districtCode`，不从浏览城市或GPS静默复制；城市与区划从属关系由服务端验证 |
| 公开地图位置 | 单独审核的 `public_map_locations` 表，和浏览偏好、发布属性、GPS独立；默认不公开个人信息坐标 |

选择浏览城市后，首页标签、发现、搜索与地图查询使用统一城市/区划编码。SQL 在排序和分页前过滤城市，未标注城市的历史信息不会被猜测归入东莞或其他城市。未指定城市的原查询仍兼容历史数据。城市目录存在不代表已开放当地发布与服务，原 `service_regions` 准入继续执行，未自动把全国镇街加入已开放服务区域。

## 地图找信息

- 发现页保留搜索在上、地图在下两个圆形悬浮入口。地图是独立子页面，不重复五导航；使用微信原生 `map` 渲染真实底图。
- 顶部搜索、八频道、浏览城市；地图支持手势拖动/缩放，右侧主动GPS/选城工具，“搜索此区域”读取原生可视边界后请求自有 API。
- 地图与信息抽屉双向联动：点单个标记高亮信息行；点列表只聚焦点位；明确点“查看详情”才导航。已有点位可按已加载数据分格聚合，聚合数量只代表已加载项，不冒充全城总数。
- 抽屉支持收起、半屏、展开按钮及触摸拖动处理；模拟器验证三档按钮，原始拖动事件在控制器测试中覆盖，物理手指手势仍待真机。
- 从地图返回发现，原频道、已加载信息和滚动位置保留。实际原生 `selectViewport().scrollOffset` 测得返回前后均为100，首条ID和频道一致。微信自动化 DOM 元数据读取在原生地图返回时不稳定，改用官方原生视口查询核验，没有以固定值或应用数据代替视图位置。
- 缺少Key时显示可恢复的明确提示，仍可手动拖动原生底图、按可视范围查点，或回列表检索；不会生成演示点填空。

截图：[半屏地图](geo-ui-map-half.png)、[展开抽屉](geo-ui-map-expanded.png)。图中地图业务点为明确标记的开发测试服务，合成坐标仅在开发验收模式展示；已在测试结束撤回，**不能视为真实门店资料**。底图由微信原生组件实际渲染。

## 服务端与隐私限制

- 新增迁移 `013_public_map_locations.sql`，只追加独立表与城市/经纬度索引，未改历史迁移或已有业务地址。持久开发库已应用迁移；原数据保留。
- `GET /api/v1/feed` 新增城市/区划参数；`GET /api/v1/map` 统一接受城市、区划、分类ID、业务类型、关键词、边界框和分页。每页50条，SQL读取51条判定后续；不存在418套地图接口。
- 地图读取每次重新检查源商家/服务公开状态、商家启停、服务区域启用、点位核验状态与测试数据隔离；暂停服务后点位立即不再返回。
- 当前只允许已公开商家或可预约服务具有地图点位。个人房产、闲置、需求、招聘、活动、公共信息尚未完成位置授权规则，因此不在地图自动公开坐标。频道仍存在，没有虚构可定位内容。
- 点位写入仅通过管理员登录及CSRF校验的 `PUT /admin/api/map-locations/:id`，必须提供核验说明、城市/区划和精度，保留审核操作记录。个人发布，即使类型叫service，也不能冒充商家服务取得精确点位。
- 近似点在写入时即保留两位小数，原始精确坐标不落入该近似点记录；公开接口不返回内部核验说明。
- `GET /api/v1/geo/reverse`、`/geo/center` 仅代理固定腾讯位置服务地址，密钥留在服务端，带超时、缓存、输入校验及限流；错误不会回显Key或GPS。
