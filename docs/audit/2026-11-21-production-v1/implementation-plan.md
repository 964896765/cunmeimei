# 村美美 V1.0 分阶段实施计划

阶段 1 已完成工作区审计。本计划沿用现有小程序、API、后台、数据库和官网。下列改动从阶段 2 开始。每阶段保留环境类型、版本／提交、执行命令、退出码、通过／失败／跳过、脱敏日志、证据链接及回退条件。隔离数据、供应商夹具、浏览器模拟与生产／真机记录分别标记。

## 阶段 2 · 后端、数据库及发布审核基础

1. 冻结本次审计基线，在当前实现上逐项修改。更新旧编辑烟测和恢复演练夹具，使之符合当前真实性确认、行业专项审核等要求；保留未确认应拒绝的测试。以 Linux 上的 Node 22 LTS、PostgreSQL 16 和锁文件干净安装建立构建基线，确认原生 Sharp 及共享分类、法律文档可以正常加载。
2. 沿用当前描述校验及 001–034 历史。新增迁移只向前，迁移、业务和备份角色分离。给普通用户、商家、运营、审核和超级管理员明确权限，补后台个人身份、停用、授权与个体审计。校对后端所有权限、CSRF、身份隔离和越权拒绝。
3. 完成普通图片上传、缩略图、草稿、发布、人工审核、拒绝、重提、撤下、过期、归属和公共可见性测试。沿用闲置模板和审核补齐转让／求购／交换用途，按用途校验字段并兼容旧业务数据。保留生产证照停用保护，实施有审计记录的线下材料受理或经安全验收的私有存储方案。
4. 加根路径 `/health` 并保留现有版本化健康和 readiness。增加受控日志字段、关联 ID、备份和告警制品；生产运行角色和备份角色使用各自的最少权限。

**完成证据。** Linux Node 22 构建和启动，PG16 全量及严格回归零失败／零跳过。提供非超级用户真实读写、不可越权、迁移清单、图片正反例、两个账号隔离和后台审核流水。空库安装和旧库副本恢复／升级均验证，现有业务行数及不变量保留。

## 阶段 3 · 微信、手机号短信与统一账户

1. 保留 `wx.login → jscode2session → OpenID → UUID` 及版本化同意。新增登录时间、会话来源和续期轮换管理，对比当前七天 Bearer 的兼容和退出语义。验证重复／并发登录保留同一个 UUID，账号状态、解绑和注销能撤掉相关会话。
2. 沿用 `verified_phones` 的加密和归属设计，新增短信发送账本和一次性挑战。归属冲突先在副本查重，保留存量身份和数据，歧义交人工核验。号码变更以前置验证和原授权撤销为条件。
3. 拟提供 `POST /api/v1/auth/sms/send`、`POST /api/v1/auth/sms/verify`、`POST /api/v1/auth/sms/login`、`POST /api/v1/me/phone/sms`，复用并加固 `DELETE /api/v1/me/phone`，新增 `POST /api/v1/auth/refresh`。校验端若单独存在，只交付绑定业务场景、短时且可单次使用的证明。校验结果、归属及消费与绑定／登录写入以事务协调。未绑定号码不可建号。
4. 短信使用安全随机六位数字，哈希存储，五分钟过期，至少 60 秒冷却，最多五次失败，成功销毁。按手机号、IP、场景限制，加入每小时／日及全站开销限额。覆盖并发、重放、供应商超时、重复发送和账号状态，日志去除号码明文和验证码。短信签名、模板编号、生产授权与费用阈值从阿里云受控核验。
5. 小程序沿现有登录、号码验证和返回流程补短信入口，继续兼容微信授权。更新隐私处理说明、第三方处理目的和用户撤销方式。

**完成证据。** HTTP 与真实隔离 PG 的正常／过期／五次失败／重放／重复归属／解绑／封禁／注销测试，短信 provider 夹具明确标记。微信错误码测试使用夹具。真实微信、签名和模板核验、真实短信回执进入阶段 6。正式密钥在批准后经服务端安全通道配置。

## 阶段 4 · 生产制品、备份与部署

1. 在本地生成带 SHA-256 清单的官网 V1.2.0 候选、API／后台发布包、Nginx 独立站点、进程监督和备份／告警制品。API 制品包含必要的 `backend/src`、`backend/admin`、`backend/legal`、迁移和引用到的小程序共享模块。依赖在目标 Linux 架构安装，输出精简制品。白名单排除开发密钥、本地状态、测试身份和资料。
2. 获准后只读确认 ECS 架构和现状，记录 Nginx 虚拟主机、日志、证书、端口、系统服务、真实数据库、磁盘、SSH、阿里云安全组及 Aegis。原配置、证书及已有数据完整备份，验证校验和和可恢复性，再申请具体生产写入。Aegis 先查异常原因，待用户确认维护窗口后才允许重启。
3. 部署建议采用宿主机 Nginx、systemd 单 Node 进程和本机 PostgreSQL 16，减少 2GB 机器常驻开销。若现场需要容器，仍只映射本机 API，PG 留私网。初始容量预算按实际可用约 1.7GiB 设定，预留约 300MiB 或更多余量。参考 PostgreSQL 共享缓冲 128MiB、最多约 25–30 个连接，API 池约 10、堆约 256MiB，结合 Sharp 解码、备份和实机并发调小。Redis 暂不引入，Swap 仅作安全余量。Nginx 独立配置、独立日志，上传路径匹配现行 2 MiB 请求体限制并保持应用侧校验，按受控代理地址覆盖可信头。
4. 如果是全新库，使用批准的生产初始化身份运行当前经复核迁移，隔离开发数据。若发现真实旧库，先做只读版本／schema／角色／数据量清单，备份数据、私有文件、角色权限和密钥恢复材料。在新库恢复并对比后，再在维护窗口对正确目标执行。生产迁移前检查应用兼容和回滚点。
5. DNS 分区域审批。主区 `dgqfl.xyz` 添加 `@ A 8.156.72.144`、`www CNAME dgqfl.xyz`。独立 `api.dgqfl.xyz` 区添加 `@ A 8.156.72.144`。现有 NS、MX、TXT 和验证记录保留。如果没有 DNSPod API 授权，提供控制台操作卡及配置前快照，待用户完成后从权威和独立解析器复核。
6. 证书分别覆盖主域／www 与 API，开放经批准的 80/443，配置自动续签、校验 HTTPS 和 HTTP 跳转。API 默认回环监听，PG 5432 和 API 3000／3100／3101 等内部端口从外网验证不可达。安全组、UFW 和 SSH 限制先安排可回退访问路径。小程序体验版先配批准的 request、uploadFile、downloadFile 实际域名和微信隐私指引。
7. 备份采用加密异地副本、明确保留、分离权限和告警。以 RPO ≤24 小时、RTO ≤4 小时作为首期演练目标，实际承诺以结果为准。验证业务库、私有文件、加密密钥、运行角色和应用版本同点恢复，并记录恢复耗时。

**完成证据。** 制品与校验和、现场基线／变更差异、可读备份及独立恢复结论、迁移校验、官方站和 API TLS 链、`/health`／`/api/v1/ready`、Nginx 日志和续签检查、重启后自启、端口隔离。官网七页、独立 404 和旧虚拟主机不受影响均有实测。阶段 4 验证部署环境，正式流量由阶段 6 放行。

## 阶段 5 · 业务闭环与权限复验

按已有入口验收五主导航、地图、统一搜索及 27／83／418 分类。七模板逐类执行草稿、普通图、待审、驳回、重提、审核公开、搜索、撤下和通知，验证公开列表与地图只显示有效内容。补齐个人管理的历史可达性、后台与商家分页、正式入驻材料和审核进度。使用不同账号执行电话逐条授权与撤销、私信和屏蔽、收藏、举报、核验、预约、积分账本及非现金兑换退还。导出、隐私请求和注销按获准的保留政策核查，保留现有关闭的公开互动及未放行的悼念入口。通用反馈工单和微信订阅依运营能力排期。

**完成证据。** 脱敏的前端入口、HTTP 路径、数据库表及状态记录、后台个人审计及可复现回归。每条核心闭环记录账号角色、请求号、时间和状态转换；明确依赖外部资质或被产品规则关闭的项目。

## 阶段 6 · 正式环境验收与上线判定

1. 用获准的 Android、iPhone 与测试账号验微信授权、取消、退出、重登、过期和续期，验证域名、上传、下载和弱网。经用户确认测试号码、场景、次数及时间窗后，实发阿里云验证码，核对 provider 请求／回执、手机实收及短信验证、绑定、登录同一 UUID 与解绑。证据只保留脱敏结果。
2. 在许可的正式验收范围内执行测试名单和逐条业务验收。覆盖数据库读写、图片访问权限、发布与人工审核、收藏、私信、举报、商家入驻、积分、导出与注销。确认测试内容可撤下并按事前约定清理，审核和数据留痕仍符合规则。
3. 完成短时并发和故障、异常文件、权限、连接恢复、日志、内存及磁盘验证。需要重启或故障注入的生产操作单独申请。P0 全部通过后提交上线报告，列出 P1/P2 待办、实际地址、接口、表、证据、容量、监控和回滚恢复结果，取得正式放行后开放流量。

## 审批和回滚

| 用户需先确认的操作 | 确认前说明和回退准备 |
| --- | --- |
| 生产服务器写入或配置修改 | 确切主机、文件和服务、替换差异、现有业务影响、快照、配置校验和原版本回切。 |
| DNS 修改 | 两区精确记录、现有记录和 TTL 快照、解析传播与证书影响、逐条还原方法。 |
| 真实短信 | 经安全渠道提交的测试号码、签名及模板、场景、发送上限、时间、费用及中止方式。 |
| 密钥配置 | 凭证类型、授权范围、服务端注入与文件权限、轮换和撤销；提交确认材料不包含秘密值。 |
| 不可逆迁移 | 目标库、迁移清单、锁和停写影响、有效备份与恢复演练、增量写入补偿和切换回原库条件。 |
| 服务器重启 | 待重启原因、受影响服务、维护窗口、控制台应急入口、重启前备份、重启后验证与恢复步骤。 |

应用优先回切已验证可兼容当前 schema 的上一版本，官网回切独立静态版本目录。数据库结构不兼容时先停写，恢复到新库并核对备份后新增的合法数据，再受控切换。保留原库与审计证据。旧迁移记录和已有业务数据须保持可追踪。
