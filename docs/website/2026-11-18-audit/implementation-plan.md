# 官网具体开发计划

这是下一步本地开发与验收方案，不是已实现功能清单。生产部署在全部制品可审阅且获得人工确认后单独执行。

## 目录与技术选择

采用 Node ESM 静态生成 + HTML/CSS + 少量原生浏览器 JS，独立 package.json，优先不引入第三方运行时依赖。七页内容在构建时生成，共用布局和品牌配置；搜索引擎及无 JS 浏览器可直接读取正文。既有项目没有 Web 前端框架，单纯为七个说明页面引入 React/SSR 没有必要。构建工具使用受支持的 Node LTS 并固定实际验收版本；不升级或替换原 API 的 Node 环境。

```text
city-life-miniapp/
├── miniprogram/                    # 保持原位
├── backend/                        # 保持原位，含现有 admin
├── apps/
│   ├── website/
│   │   ├── package.json            # 独立 build / dev / test 命令
│   │   ├── .gitignore              # 独立忽略 dist 与预览产物
│   │   ├── src/
│   │   │   ├── site.config.mjs     # 主体、备案、联系、小程序码配置
│   │   │   ├── content/            # 七页内容及官网法律说明
│   │   │   ├── layouts/            # 公共导航、页脚、正文布局
│   │   │   └── styles/             # 官网蓝白设计规范，不回写小程序
│   │   ├── public/                 # 经确认的 logo / 小程序码 / 公共资源
│   │   ├── scripts/                # 构建和仅回环监听的本地预览
│   │   ├── tests/                  # 路由、内容、链接和构建安全检查
│   │   └── dist/                   # 构建输出，独立发布包
│   └── admin/README.md             # 仅范围预留说明，不构建新后台
├── infrastructure/nginx/
│   └── dgqfl-website.conf.example  # 官网专属虚拟主机，核实后配置
└── docs/website/                    # 设计、验收、部署与回滚文档
```

不搬迁目录，不新增根工作区，不要求 backend 安装官网依赖，不从官网脚本调用数据库/迁移命令。未来 admin 预留目录仅说明规划，与现有 backend/admin 无替代关系。

## 页面与视觉

| URL | 内容与行为 |
| --- | --- |
| `/` | 品牌、指定主副标题、六类业务、平台特色、五步使用流程、真实小程序码配置区域 |
| `/about` | 定位、运营主体、信息服务模式、实际开放范围、线下交易说明 |
| `/services` | 六类业务各自的介绍、适用场景、使用方法和开放条件，不提供网页信息列表或发布 |
| `/help` | 九项指定帮助；按现有小程序源码写入口，未开放能力明确提示 |
| `/agreement` | 官网使用规则及适用范围，展示小程序服务协议时单独标明范围、版本、有效日期 |
| `/privacy` | 官网访问日志与小程序功能的数据处理分区说明，不把访问官网描述为微信授权 |
| `/contact` | 运营主体与服务范围，按配置展示真实联系方式及已存在的小程序隐私请求入口 |

另外生成真正返回404状态的404页，不把所有未知 URL 回退到首页。每页生成 title、description、canonical；附 sitemap.xml、robots.txt 和 favicon。

视觉使用蓝白、中性色与品牌蝴蝶标识，桌面宽幅排版、移动端单列；轻量半透明导航、克制阴影、清晰字体层级。首页以品牌和身边生活场景展开，不复制后台布局，不制作虚假用户评价、统计数字或服务商案例。

导航使用真实链接并标明当前页。移动菜单支持键盘、焦点和关闭；FAQ 可使用原生 details。提供跳至正文、可见焦点、足够触摸区域；尊重减少动态效果设置。使用系统中文字体及本地资源，首期不接外部字体、统计追踪或第三方嵌入。

小程序码未配置时使用文字入口说明和可配置素材位置，不生成仿真码、不设置无效扫码按钮。不虚构一键唤起链接；如后续提供真实 URL Link，再作为可选配置验收。

## 开发批次与交付

| 批次 | 工作 | 完成条件 |
| --- | --- | --- |
| W1 独立骨架 | 新目录、配置、共享布局、七页静态路径、404、构建/预览 | 单独构建可运行，原项目无需变更 |
| W2 内容与视觉 | 首页设计、六类内容、帮助、联系方式空态、法律文案范围区分 | 桌面/手机可审阅，内容逐项有真实依据 |
| W3 本地验证 | 全站链接、直达/刷新、404、移动菜单、布局、静态包白名单、无业务接口请求 | 自动化结果、浏览器截图、未测事项清单齐全 |
| W4 部署制品 | 官网 Nginx 模板、独立静态目录、备份与回滚操作文档、发布包校验和 | 配置不含 API 代理或业务文件；证书/路径待核实项明确 |
| W5 上线前核验 | 授权方式明确后只读核验目标主机、DNS、证书、备案对应关系、资源与现有站点 | 填入真实路径，提交具体配置差异和制品供人工确认 |
| W6 人工确认后部署 | 备份、独立目录上传、nginx -t、受控 reload、域名回归 | HTTPS、www跳转、七页、404及原API基线检查完成 |

W1—W4 可在本地推进，无须访问生产或等待联系素材；W5—W6 不把未知生产信息替换为猜测值。未确认前不上传文件、修改 DNS、申请证书或 reload 生产服务。

## 静态路由和隔离部署

构建生成 `about/index.html` 等真实页面，Nginx 对明确的七条路由提供对应文件，规范化尾斜杠与 canonical，未知路径返回404。预览服务器复用相同路由规则，测试刷新与直接访问。

建议官网专属目录 `/srv/dgqfl-website/releases/<release-id>/`，`current` 链接指向当前制品；该路径是建议，必须先核实不占用现有目录。Nginx root 只指向 dist 内容，不暴露仓库、backend、.env、附件或私有资料。官网虚拟主机精确匹配根域/www，不配置 proxy_pass，不承载 `/api` 或 `/admin`。

HTTP 根域/www 均跳到 `https://dgqfl.xyz` 并保留路径；HTTPS www 先完成有效 TLS，再跳根域。证书必须同时覆盖 `dgqfl.xyz` 和 `www.dgqfl.xyz`，只有通配符证书不能覆盖根域；没有合适现有证书时记录阻塞，不自行签发或替换。默认站点及原 API/admin 虚拟主机保持原配置。

共享 Nginx reload 仍可能影响已有站点：实际应用前备份原配置、检查 server_name 冲突、记录原 API 健康基线，执行 nginx -t，通过后才 reload，并立刻复查 API。不能仅凭“独立 conf 文件”承诺线上零影响。

## 验收和回滚设计

- 自动化：七页状态与内容、导航/页脚链接、未知路径404、直达/刷新、恶意路径不能读仓库、正确主体/ICP备案链接、无占位二维码、可配置空字段、安全转义和静态制品白名单。
- 浏览器：桌面1440/1024，移动390/375/320视口；全站溢出、菜单、焦点、FAQ、小程序码空态与真实素材态；减少动效；无控制台错误、无业务API请求。
- 微信：本地微信 UA 仅检查兼容性，不能替代真实微信内置浏览器；实际手机打开HTTPS链接另留截图和结果。
- 部署：TLS链/有效期、80→443、www→根域、路由/刷新/404、ICP备案内容、原API健康与既有入口前后比对。真实服务尚未可访问时如实标“未执行”。
- 回滚：保留上一个静态 release，切回 current；若改过 Nginx，则恢复本次备份的官网配置并 nginx -t 后 reload，复查官网与原 API。首次部署回退仅移除本次新增的站点启用项并恢复此前状态。保留失败制品与日志，不清理业务数据、不回滚数据库、不操作小程序。

预计不新增业务接口、数据库表、迁移或服务器常驻 Node 进程；完整源码、构建包、截图、测试报告和实际文件清单随 W1—W4 交付。
